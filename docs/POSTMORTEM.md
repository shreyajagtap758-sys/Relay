## Incident 01 — Buttondown: Database Connection Exhaustion (Week 0, Day 3)

**Source:** [Buttondown incident 0024](https://buttondown.com/blog/incident-0024)
*Summary paraphrased; see source for the full writeup.*

**What broke:** New requests could not acquire a database connection, so they failed or hung. From the outside the application looked like it had a slow or failing database.

**Root cause:** The configured connection ceiling was reached. There were no connections left to hand out, so incoming work had nowhere to go — the database itself was not the failing component.

**What I learned:** Connection exhaustion impersonates database slowness. The symptom (requests taking long or failing) points at the database, but the actual constraint sits in the application's connection layer. Debugging in the wrong layer is the default failure mode here.

**Evidence from my own experiments the same day:** I reproduced this shape locally with `pool_size=2` and 10 concurrent 1-second queries.
- Total time was **5.25s** for work that was only 1 second deep, because requests queued for connections. REQ 10 reported **5.20s latency for a 1s query** — roughly **4.2s of pure waiting**.
- With `pool_timeout=1` the failures surfaced as `QueuePool limit of size 2 overflow 0 reached, connection timed out` — thrown by **SQLAlchemy, not Postgres**. Those requests never reached the database, which means Postgres-side monitoring would have shown a perfectly healthy database while 8 of 10 requests failed.
- Raising `pool_size` to 10 dropped total time to **1.66s**, confirming the pool was the bottleneck.

**What this means for Relay:**
1. I have never consciously chosen a `pool_size` — it has always been a default I ignored. That is an unowned failure mode. → future `DECISIONS.md` entry.
2. `workers × pool_size` must stay under Postgres `max_connections` (default 100), otherwise the failure moves to a different layer with a different error (`FATAL: sorry, too many clients already`) and a different fix.
3. Latency alone cannot detect this. Relay's observability needs **error rate and pool wait time** alongside latency, because a fail-fast config makes latency graphs look *better* while dropping work.
4. Enqueue needs a deliberate saturation policy — wait, or reject with 503 and let the caller retry. Silent waiting is the default, and defaults are how incidents like this happen.

**Still to verify:** I have not yet confirmed with `pg_stat_activity` that my configured pool size matches the actual connection count on the server side, and I have not read the full writeup closely enough to capture their detection and remediation timeline. Both are follow-ups.

## Incident 02 — Cloudflare: Catastrophic Regex Backtracking and WAF CPU Exhaustion (July 2, 2019)

**Source:** [Details of the Cloudflare Outage on July 2, 2019](https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/)
*Summary paraphrased; see source for the full writeup.*

**What broke:** Global HTTP proxy traffic dropped by roughly 80% for 27 minutes. Cloudflare edge nodes worldwide returned `502 Bad Gateway` errors due to CPU exhaustion in the processes that serve HTTP/HTTPS traffic `[SOURCE]`. Two corrections to my first draft: the writeup says **"nearly 100%"**, not 100%, and it never names **NGINX**. Cloudflare's Lua WAF did run inside their NGINX-based proxy, but that is background knowledge I brought, not something this postmortem establishes `[INFERRED]`.

**A detail worth keeping, because it repeats Incident 01:** the `502`s were generated by the **front-line** web servers, which *still had CPU available* and simply could not reach the HTTP/HTTPS-serving processes behind them `[SOURCE]`. The layer that **reported** the error was not the layer that **failed** — the same shape as Incident 01, where `QueuePool ... connection timed out` was raised by SQLAlchemy while Postgres was perfectly healthy. Second time this pattern has appeared in two postmortems.

**Root cause:** A new managed XSS detection rule containing unanchored, adjacent quantifiers (`.*.*=.*`) was deployed globally in a single push without staged canary rollout. When evaluating standard HTTP request bodies, the regex engine suffered catastrophic exponential backtracking, pinning all CPU cores on proxy servers.

**What I learned (Protection vs Coverage):**
- **What they believed was protecting them:** 
  1. A staging pipeline where rules are tested for functional correctness before shipping.
  2. **"Simulate" mode.** This is the strongest item in the whole incident and my first draft missed it entirely. The rule was deployed in simulate mode, where real customer traffic passes through the rule but **nothing is blocked** `[SOURCE]`. The mental model is *"simulate = nothing happens"*. The actual coverage was *"nothing gets **blocked**"* — the rule still had to **execute** to be evaluated, and executing it was the entire failure. A protection whose name describes the write path while the cost lives on the execution path.
  3. The regex engine itself. Source item 3 of *What went wrong*: the engine **had no complexity guarantees** — PCRE, backtracking, and per the writeup "no mechanism to protect against a runaway expression" `[SOURCE]`. (My first draft guessed at an assumption here — "regex rules could not saturate all server resources". The source states the real thing, so the guess is replaced.)
- **What was actually covering them (and what failed):**
  1. **Protection removed during refactoring:** An explicit CPU-consumption limit/guard in the Lua WAF engine had been removed weeks earlier during a refactoring of the WAF. The source's exact framing is **"removed by mistake"** `[SOURCE]` — not a judgement call that it was no longer needed, which is what my first draft claimed. That distinction matters: nobody weighed this protection and decided against it, so there was no decision anyone could have reviewed.

     And the irony is in the source, not added by me: **the refactoring's purpose was to make the WAF use less CPU** `[SOURCE]`. A CPU optimisation removed the CPU guard. The safety net existed, was deleted as collateral, and nothing in the process noticed its absence for weeks.
  2. **Test suite blindspot:** Test suites validated functional matching (does it catch XSS?) but completely omitted performance testing (how much CPU does it burn on non-matching inputs?). The sharp part: the source notes that examining log files from previous WAF builds showed **no increase in test-suite run time** for the offending rule `[SOURCE]`. So the signal was not merely absent — a weaker version of it was being *recorded and not read*. That is `P-18`'s shape (a check whose output nobody consumes) rather than `P-04`'s (a check that covers less than it appears to).
  3. **Staged rollout bypassed:** Security rules were exempt from the standard gradual/canary release process to enable fast deployment against threats, turning a bad rule into an instantaneous global failure.
  4. **Shared Failure Domain in Recovery:** The outage lasted 27 minutes partly because engineers could not access their internal control panel—the authentication service (Cloudflare Access) ran behind the very proxy that was down. Recovery tooling shared the failure domain with the failing system.

     The cost is measurable from the source's own timeline, so it should be stated as a number rather than as "partly" `[SOURCE]`: the WAF was identified at **14:00**, the global terminate was **proposed at 14:02**, and **executed at 14:07**. Traffic recovered by **14:09**. So roughly **five of the twenty-seven minutes** sat between knowing the fix and being able to apply it. Two compounding details: Cloudflare Access being down blocked authentication to the internal control panel, and some SREs had **lost their credentials entirely** because a security feature times out accounts that do not use the internal panel often. The bypass procedure existed but was rarely drilled.

  5. **The rollback path was slower than the failure path.** Source item 6: the rollback plan required running the complete WAF build **twice**, which took too long `[SOURCE]`. This is the one I would have least expected and it is the most directly transferable: the deploy path was seconds (Quicksilver, p99 **2.29s** globally) and the undo path was minutes. Speed was engineered in one direction only.

  6. **Detection lagged too.** Source item 7: the first alert for the *global traffic drop* took too long to fire `[SOURCE]`. WAF-specific synthetic tests paged within three minutes (13:42 deploy → 13:45 first page), but the alert for the thing that actually mattered — traffic falling off a cliff — was not the fast one.

**One framing note from the source that this template fights against.** The writeup explicitly refuses single-root-cause analysis: *"Getting to a single root cause, while satisfying, may obscure the reality"*, and it lists **eleven** converging causes `[SOURCE]`. My **Root cause** heading above names one. Keeping the heading but recording that the source rejects the framing, because the postmortem shape I am reusing has a `Root cause` field and this incident is the argument against trusting that field.

**Evidence from my own experiments / Relay connection:**
- **[INFERRED — Relay extension]:** In Week 0 and Week 1 experiments (`P-15`, `P-02`), I observed that Relay bounds nothing: a worker running a long handler stays fully alive in the OS process table while queue progress stops.

  **But the two examples in my first draft are not the same thing, and collapsing them is wrong.** `await asyncio.sleep(...)` **yields** to the event loop — other tasks in that process keep running. A large synchronous `json.loads` or a backtracking regex **does not yield**, and starves every other coroutine in the process. My own `P-08` already draws this line ("a large `json.loads` is CPU-bound synchronous work inside an async event loop", with Week 0 Day 1's `6.04s vs 2.04s` measurement behind it). Cloudflare's failure is the **second** kind. Only the second kind is the analogy.

  This also means the *"Still to verify"* line at the bottom of this entry is the right open question, and the body must not read as if it were already answered.
- `P-13` showed that Relay cannot tell how many workers are alive or what they are doing. A live PID provides zero evidence of job progression.
- `P-06` showed that an internal failure cannot be resolved from within the blocked participants; resolution required `pg_terminate_backend` from an external supervisor.

**What this means for Relay:**
1. **Liveness is not progress [INFERRED]:** Process-level monitoring only detects crashes (`SIGKILL`, exit != 0). A stuck handler leaves the process alive while stranding work.
2. **Reaper must not share a fate with workers:** The Reaper must run as a completely independent process/loop. If the Reaper runs inside the worker process, a worker stuck in CPU/event-loop starvation will also freeze the Reaper.

   **And a separate process only narrows the shared fate, it does not remove it** — the same wording discipline that applies everywhere else in these docs applies here. Relay's reaper and its workers share **one Postgres instance**, and `P-06` is the proof that this is not theoretical: a session holding locks in that shared database froze an operation that had nothing to do with it. Cloudflare's version of this was Access sitting behind the proxy it was supposed to help recover. So the honest claim is: *a standalone reaper removes the CPU/event-loop shared fate and keeps the database shared fate.* Week 2's reaper should carry a `lock_timeout` for exactly this reason (see Incident 03).
3. **Lease without handler timeout enables duplicate work:** `P-15` established that mid-job graceful shutdown is bounded only by the handler — and per `P-15`'s own status line that measurement was taken **by the reviewer**, so it is `[MEASURED-R]`, not a number I can defend without re-running it. "Proved" is downgraded accordingly. If a handler outlives its lease, the Reaper reclaiming the row allows a second worker to execute the same job, creating duplicate side effects (Contract #2 violation).
4. **Safety mechanisms must not be refactored away:** Removing an unmeasured safety check (like a CAS guard or payload size limit) without verifying the worst-case blast radius is how global outages happen.
5. **"Dry-run" bounds the write, not the execution — and Din 2 will tempt me with exactly this.** The simulate-mode fact is not a Cloudflare curiosity; it is a trap already waiting in Week 2. A reaper run in dry-run mode, logging what it *would* reclaim, still evaluates the full predicate, still holds the same locks, and still competes for the same connections. Whatever is expensive or wrong about the predicate happens in dry-run too. The only thing dry-run buys is that no row changes state. So "I tested it safely in dry-run first" is a claim about the **write**, and I should not let it become a claim about **cost or correctness**.

**Still to verify:** I have not yet measured how CPU-bound synchronous work in Python (e.g., large `json.loads` or regex evaluation) starves the `asyncio` event loop compared to I/O-bound awaits in `worker.py`.

## Incident 03 — Relay Internal: Abandoned 'idle in transaction' Sessions Freeze Routine DDL (Week 1, Day 1)

**Source:** Internal project incident [`P-06`]
*Measured directly on local PostgreSQL 16 Docker instance.*

**What broke:** A routine cleanup DDL statement (`DROP TABLE counters, doctors;`) hung indefinitely. The query blocked without error, returning no output and locking the migration workflow.

**Root cause:** Four abandoned PostgreSQL backends from the Week 0 Day 5 experiments were still open. **Correction to my first draft: they were not all `idle in transaction`.** `P-06`'s own table records four *different* states — PID 38 plain `idle`, PID 45 `idle in transaction (aborted)`, PID 53 `idle in transaction`, PID 61 `active` and already blocked. Only **two** of the four held a transaction open. Writing "four sessions in `idle in transaction`" contradicts my own measurement and also destroys the most useful part of the observation, which is that the four states are **not interchangeable**: the plain `idle` session held nothing and blocked nobody. One of these sessions held a table lock that conflicted with the `ACCESS EXCLUSIVE` lock demanded by `DROP TABLE`.

**What I learned (Protection vs Coverage):**
- **What I believed was protecting me:** 
  1. I assumed that when a client script finishes or disconnects, PostgreSQL automatically cleans up uncommitted transactions.
  2. I assumed a database has a default safety timeout that terminates abandoned idle transactions.
- **What was actually covering me (and what failed):**
  1. **Assumed protection was disabled by default:** The setting `idle_in_transaction_session_timeout` is `0` (disabled) on this instance. **Now measured rather than assumed** `[MEASURED-R 2026-08-22, reviewer, this machine]` — `pg_settings` on the running container, Postgres **16.14**:

     | `name` | `setting` | `source` | `boot_val` |
     |---|---|---|---|
     | `idle_in_transaction_session_timeout` | `0` | `default` | `0` |
     | `idle_session_timeout` | `0` | `default` | `0` |
     | `statement_timeout` | `0` | `default` | `0` |
     | `lock_timeout` | `0` | `default` | `0` |
     | `tcp_keepalives_idle` / `_interval` / `_count` | `0` | `default` | `0` |

     **`source = default` is the load-bearing column**, not the value: nobody set these, so nothing here was a decision. And the finding that neither `P-06` nor my first draft had: **it is not one missing bound, it is five.**

  2. **`lock_timeout = 0` is why the symptom was a hang instead of an error.** This is the new angle. `idle_in_transaction_session_timeout` explains why the *culprit* survived; `lock_timeout` explains why the *victim* waited silently and forever instead of failing fast with `canceling statement due to lock timeout`. Two different settings producing two different halves of the incident, and I had been treating it as one cause. Directly a Week 2 concern: **the reaper's own statements need a `lock_timeout`**, otherwise the reaper can become a blocked victim and stop reaping while still appearing alive — which is Incident 02's liveness-is-not-progress lesson landing inside Relay's own recovery mechanism. The database will happily hold open locks forever for an idle connection until explicitly killed or restarted.
  2. **Resolution had to come from outside:** Blocked sessions could not proceed, and the culprit session was idle and unaware it was blocking others. **Recovery came entirely from the outside** via `pg_terminate_backend` issued by an operator. This is the exact architectural justification for Relay's Reaper.

**Evidence from my own experiments (`P-06` blast radius table):**
Inspecting `pg_stat_activity` revealed the following multi-session lock contention before termination:

| PID | State | Wait Event Type / Event | Query / Activity | Role in Incident |
|---|---|---|---|---|
| **38** | `idle` | `Client` / `ClientRead` | `SELECT * FROM counters;` | **Bystander** — no open transaction, no locks held, blocked nobody. This row is why the others are readable |
| **53** | `idle in transaction` | `Client` / `ClientRead` | `SELECT * FROM doctors WHERE on_call = true ...` | **Culprit** — holding row locks from an uncommitted transaction |
| **61** | `active` | `Lock` / `transactionid` | `SELECT * FROM doctors WHERE on_call = true ...` | **Victim 1** — blocked on PID 53's transaction id, continuously, since the Day 5 experiment ended |
| **45** | `idle in transaction (aborted)` | `Client` / `ClientRead` | `SELECT value FROM counters WHERE key='foo'` | **Lock holder, blast radius not established** — the transaction had already failed and could do nothing useful, yet still held its locks. Whether the `DROP` was queued behind 45 or 53 was **not determined** before the sessions were killed |
| **1724** | `active` | `Lock` / `relation` | `DROP TABLE counters, doctors;` | **Victim 2** (blocked waiting for `ACCESS EXCLUSIVE`) |

- **Uncertainty on duration:** The container uptime was ~5 days, providing an **inferred upper bound** for transaction age; exact `xact_start` duration was not recorded before terminating the sessions.
- Once `pg_terminate_backend` was executed on **every** stale session, the blocked `DROP TABLE` returned immediately. **The "12ms" in my first draft was invented and has been removed** — `P-06` records "returned immediately" and no timing was captured. Reconstructed latency: **not recorded.** This is the exact failure the reviewer contract's rule 6 names (do not fill a plausible value where a field was not measured), and it is worth leaving the removal visible rather than silently deleting it.

**What this means for Relay:**
1. **Self-resolution is impossible for abandoned state:** A crashed, hung, or disconnected worker cannot rollback or release its own locks if the TCP socket stays half-open. Recovery must be external (a standalone Reaper process).
2. **`idle in transaction (aborted)` still holds locks:** Even after an error aborts a transaction, PostgreSQL holds all acquired locks until `ROLLBACK` or connection termination.
3. **Database defaults are not production safety nets:** Relay cannot rely on default Postgres timeouts. Explicit application-level bounds (handler timeouts + reaper lease sweeps) are mandatory.

**Still to verify — narrowed, not closed.** The `pg_settings` read above establishes that `tcp_keepalives_idle/_interval/_count` are all `0`, which in Postgres means *defer to the OS default* rather than *disabled* `[MEASURED-R]`. So Postgres is not setting a detection window at all; whatever window exists belongs to the container's OS and is on the order of **hours** on Linux defaults `[INFERRED — not measured on this machine]`. Two things still open, and the first one is now the sharper question: whether a *live but idle* psql client is ever reaped at all (it should not be — `ClientRead` with a healthy socket is normal), which means the "dead client" framing in my first draft was itself unsupported: `P-06` never established that those clients were dead, only that they were **idle**. I have not yet measured how long Docker Desktop / OS TCP keepalives take to detect a genuinely dead client socket and close an idle backend session when `idle_in_transaction_session_timeout` is left at `0`.
