# PROBLEMS.md

Interesting problem explorations and edge cases encountered during Relay's development.

## P-01 — A retry is not a reliability feature; it is a correctness hazard

**The problem:** When a call fails, the obvious instinct is to retry. But whether retrying is *safe* depends entirely on **which kind of failure** occurred — and the two kinds are easy to confuse because both surface as "the call failed."

- **Connect timeout / connection refused** → the handshake never completed, so the request never reached the server. Nothing happened on the other side. Retrying is completely safe.
- **Read timeout / silent drop** → the connection was established and the request *was delivered*. The server may have fully processed it — charged the card, sent the email — and only the response was lost. Retrying may duplicate the side effect.

**Why this is interesting:** it inverts how I used to think about retries. I treated retries as a way to *add* reliability. In reality a retry is a **decision to risk duplicate work in exchange for a chance at completion**. The failure type tells you whether that risk is zero or real.

And the uncomfortable part: after a read timeout, there is **no way to find out** which happened. The information does not exist on my side. So the choice is between possibly losing the work and possibly doing it twice.

**Why it matters for Relay:** this is the actual justification for idempotency keys — not a best practice picked up from a blog, but a direct consequence of the fact that a read timeout is unresolvable. Safety cannot come from the retrying side; it has to come from the receiving side being idempotent. This becomes Week 3's dedup design, and the open question of whether the idempotency key should be supplied by the caller or generated by Relay.

## P-02 — A timeout looks like a guarantee in code, but it is only a request

**The problem:** Writing `timeout=0.5` reads like a hard promise: this operation will not exceed 0.5 seconds. My Day 4 measurement suggested otherwise — a read timeout set to `0.5s` aborted at `2.172s`, which matched almost exactly the 2-second sleep on the server being called.

The likely explanation is that the timeout fired on schedule, but **cancelling the in-flight socket read was deferred** until that I/O operation actually completed. The abort could only take effect once the server finally responded. 

**Why this is interesting:** it is structurally the **same shape as Day 2's signal handling.** There, `SIGTERM` arrived on time and the handler ran on time — but it could not preempt the loop that was already running; it could only set a flag and hope the loop checked it. Here, the timeout fires on time but cannot preempt I/O that is already in flight.

Two completely different mechanisms — OS signals and socket timeouts — turn out to share the same limitation: **you can request that something stop, but whether it stops promptly depends on whether the runtime can interrupt what is currently executing.**

A second, related trap in the same family: a per-phase `read timeout` measures the *gap between chunks*, not the total lifetime of the request. A server that sends one byte every 0.4s against a 0.5s read timeout will hang **forever**, because the stopwatch resets on every byte. The configuration looks protective and provides no protection at all. Real protection requires a separate overall deadline.

**Why it matters for Relay:** any place where I "set a timeout" and assume boundedness needs checking. A timeout bounds *intent*, not *reality*. In Week 2 this decides how much I can trust a lease deadline: if a worker cannot be interrupted promptly, lease expiry does not stop it — which is precisely how one job ends up executing twice with both executions being legitimate.
## P-03 — "Give me the oldest pending job" is a harder query than it looks, and I am not allowed to guess the answer yet

**The problem:** Relay's worker claim query is, in plain words: *"give me the oldest job whose status is `pending`."* Roughly:

```sql
SELECT id FROM jobs
WHERE status = 'pending'
ORDER BY created_at, id
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

Two open questions sit inside it, and both are index questions:

1. **Which index does this actually need?** A plain index on `status` seems obvious, but the query also sorts by `created_at`. A composite index on `(status, created_at)` could satisfy both the filter and the ordering — or the planner might ignore it entirely at small table sizes and just sequential-scan.
2. **Does the index need to cover the whole table, or only the `pending` rows?** This is the case for a **partial index** — `WHERE status = 'pending'`. The intuition is that it should be much smaller, because a healthy queue has few `pending` rows and a growing pile of `succeeded` ones. A partial index would only contain the rows the worker actually competes for.

**Why this is interesting:** the shape of the data is unusual and works *against* a normal index. In a typical table, indexed values are spread out and stable. Here, `status` has only four or five distinct values, and the interesting one — `pending` — is a **small and constantly churning** subset of a table that otherwise grows forever. Every job passes through `pending` exactly once and then leaves it. So the index's useful contents are almost entirely turnover.

There is a second effect I understand only in outline. Week 0 Day 5 established that in MVCC an `UPDATE` is internally a delete plus an insert. Every status transition therefore creates a new row version, and index entries have to track those versions. A `jobs` table is unusually update-heavy for its size — every row gets updated at least twice on its way to `succeeded`. Whether that produces meaningful index bloat, and whether a partial index makes it better (fewer entries) or worse (entries constantly entering and leaving), **I cannot reason out from first principles and should not pretend to.**

**Status: deliberately unanswered.** `WEEK_01.md` is explicit that this gets **measured** in Week 4 with `EXPLAIN ANALYZE`, not guessed in Week 1. Writing a guess into the schema today would freeze an assumption I have no evidence for, and I would then be unable to tell whether a later slowdown came from the index or from something else.

**What the measurement needs to look like when Week 4 arrives:**
- `EXPLAIN ANALYZE` on the claim query with no index, then a `(status, created_at)` composite, then a partial index — one variable per run
- Enough rows for the planner's choice to actually matter; at a few hundred rows a sequential scan will win and the comparison will be meaningless
- A realistic status distribution — mostly `succeeded`, few `pending` — because a table that is 100% `pending` would not exercise the partial index's advantage at all

**Why it matters for Relay:** this query runs on every worker poll, on every worker, forever. It is the single hottest query in the system. It is also the query that Week 4's throughput work will be about, so getting an honest measured answer matters more than getting an early one.

## P-04 — A constraint that enforces part of an invariant is more dangerous than no constraint at all

**The problem:** Day 1's schema work produced the same failure three separate times, in three unrelated places. Each time, a database constraint looked like it enforced a business rule, and each time it could only enforce a fragment of it.

| Where | The rule I actually want | What a constraint can see | Gap |
|---|---|---|---|
| `type` | A handler for this type is registered in the worker | Whether the string is in a list | The worker's handler registry is invisible to the DB |
| `status` | `succeeded → running` is illegal | The row's *current* value only | Requires old **and** new value — two versions of one row |
| Day 5 `doctors` | At least one doctor stays on call | One row at a time | Requires an aggregate **across** rows |

The general boundary:

> A database constraint can enforce an invariant only if that invariant fits inside **one row, at one point in time**. Anything spanning multiple rows, multiple versions of a row, or state the database cannot see must be enforced elsewhere — application logic, compare-and-set, or `SERIALIZABLE`.

**Why this is interesting:** the intuitive ranking is wrong. I would have ordered these as *no constraint < partial constraint < full constraint*. The middle one is actually the **worst position**, and this inverts that ranking.

With no constraint, I know I am responsible for the rule, so I write the check. With a full constraint, the database genuinely holds the line. With a partial constraint, I get a signal that the rule is handled — the migration exists, the `CHECK` is visible in `\d jobs`, code review sees a constrained column — while the actual invariant is unguarded. **The confidence is real and the protection is not**, and the gap between those two is where the bug lives.

The `type` case is the cleanest illustration. A `CHECK (type IN ('send_email', ...))` would pass `'send_email'` with no registered handler for it. The constraint did its job, the invariant was still violated, and the schema now advertises safety it does not provide.

This is also the same structural shape as Week 0's recurring lesson, arriving from a new direction. Day 2: `SIGTERM` looks like it stops a process, but it only *requests* that the process stop. Day 4: `timeout=0.5` looks like a hard bound, but it only requests one. Day 5: `REPEATABLE READ` sounds stronger than it is. And now: a `CHECK` constraint looks like it enforces a rule, but it only constrains a value. **Four different mechanisms, one pattern — the name promises more than the mechanism delivers, and the name is what I remember under pressure.**

**Why it matters for Relay:** it produces a checklist item for every future constraint, and one architectural consequence.

The checklist: before adding a constraint, write down the invariant in plain words, then ask whether it fits in one row at one instant. If it does not, add the constraint only if I can also state what it *fails* to cover — and record that gap where the enforcement actually lives.

The architectural consequence, which is already load-bearing: `status` transitions are guarded by `UPDATE ... WHERE status = 'pending'` and an affected-row-count check, not by the schema. That guard is not defensive decoration — it is the claim mechanism itself, and it is the only thing standing between Relay and Day 5's lost update. Which means the enforcement is only as good as my discipline in never writing a `status` update without it. The database will not remind me.

## P-05 — Relay has two columns that look like they give FIFO ordering, and neither of them does

**The problem:** Two of the six columns decided on Din 1 appear to give a reliable "oldest job first" ordering. Both are approximations, and for the same underlying reason.

**`id` (`bigint` identity):** sequences are non-transactional. `nextval` is never rolled back, so gaps appear. More importantly, **id assignment order is not commit order.** Transaction T1 can take `id = 5`, run for five seconds, and commit *after* T2 has taken `id = 6` and committed. `id = 6` becomes visible first.

**`created_at` (`timestamptz DEFAULT now()`):** `now()` returns **transaction start** time, not commit time. So T1 stamps `10:00:00`, runs for five seconds, and commits after T2 stamped `10:00:03` and committed immediately. Again the later-stamped row is visible first.

Two independently chosen columns, and the same flaw in both — because the cause is in neither column. It is that **the moment a row gets its identity and its timestamp is not the moment it becomes visible to other transactions.** Assignment happens at statement time; visibility happens at commit. Nothing stored inside the row can record an event that happens after the row is written.

**Why this is interesting:** it is a genuinely unfixable-by-schema problem, which is a category I had not encountered before. My instinct on reading it was "then use a better column" — a commit timestamp, a monotonic counter. But there is no column that can hold a value assigned after the row is already written. The information simply does not exist at write time.

It also reframes a claim I had accepted too easily. The usual pitch for `bigserial` is that it is monotonic. It **is** monotonic in *assignment*, and that is not the property a queue needs. A queue needs monotonicity in *visibility*. Those two are quietly different, and the word "monotonic" hides the difference.

And a third angle, which is really the same problem in a different costume: this is another instance of Week 0's core lesson that a process cannot observe another's true state. Day 2 could not tell a dead worker from a slow one. Day 3 could not tell a dead client from an idle one. Day 4 could not tell a down network from a slow one. Here, a reader cannot tell "created earlier" from "committed earlier" — and the reason is the same, that the only evidence available was recorded before the event that actually matters.

**Why it matters for Relay:** Relay's ordering is **best-effort FIFO, not guaranteed FIFO**, and that is a property to state openly rather than discover later. It is acceptable because ordering is not among Relay's five contract promises — the promises are about not losing jobs, exactly-once side effects, bounded retries, DLQ on terminal failure, and always knowing where a job is. None of those require strict arrival order.

But two consequences follow:

1. **Any ordered query needs a tiebreaker to be deterministic** — `ORDER BY created_at, id` rather than `ORDER BY created_at` alone, since jobs enqueued in one transaction share a timestamp exactly.
2. **A pathological case exists and is not handled.** A job enqueued inside a long transaction gets an old `created_at` and becomes visible much later, so it can be starved by newer jobs that keep arriving. I have not thought through how bad this can get, and it is not on any week's plan. Recording it here rather than inventing a fix.

**Genuinely open:** if strict FIFO were ever a requirement, what would it cost? A commit-time sequence number, or a single-writer enqueue path, are the shapes I can guess at — but I do not understand either well enough to evaluate. **Unresolved, and deliberately left that way.**

## P-06 — My own Day 5 prediction came true five days later, by accident, and blocked a `DROP TABLE`

**Status: MEASURED.** This was not an experiment. It happened while cleaning up Week 0's leftover tables on Din 1 of Week 1, and it is the first time a Week 0 lesson bit me for real rather than in a controlled test.

**What happened:** `DROP TABLE counters, doctors;` hung. No error, no timeout, just no return — the exact "part of the system looks frozen with nothing in any log" symptom.

`pg_stat_activity` explained it:

| PID | `state` | `wait_event_type` | `wait_event` | Last query |
|---|---|---|---|---|
| 38 | `idle` | `Client` | `ClientRead` | `SELECT * FROM counters;` |
| 45 | **`idle in transaction (aborted)`** | `Client` | `ClientRead` | `SELECT value FROM counters WHERE key='foo'` |
| 53 | **`idle in transaction`** | `Client` | `ClientRead` | `SELECT * FROM doctors WHERE on_call = true ...` |
| 61 | `active` | **`Lock`** | **`transactionid`** | `SELECT * FROM doctors WHERE on_call = true ...` |
| 1724 | `active` | **`Lock`** | **`relation`** | `DROP TABLE counters, doctors;` |

Those first four are **the psql terminals from the Week 0 Day 5 experiments — still open, roughly five days later**, with transactions never committed or rolled back.

PID 53 is still the culprit and PID 61 is still the victim, in exactly the roles recorded in the Day 5 log:

> | T2 (PID 61) | **victim**, frozen | `active` | `Lock` | `transactionid` |
> | T1 (PID 53) | **culprit**, holding lock | `idle in transaction` | `Client` | — |

**Same PIDs. Same states. Five days of continuous waiting.** PID 61 has been blocked since the experiment ended.

**Why this matters more than the original experiment:** the Day 5 log already contained the correct prediction, written as theory —

> *"And by default Postgres will NOT kill an `idle in transaction` session. Unless `idle_in_transaction_session_timeout` is configured, it can sit there indefinitely holding locks... had T1's client died at that moment, T2 would have waited **forever**."*

That was inference at the time. It is now measured: **five days, indefinitely, no intervention from Postgres.** "Indefinitely" turned out to mean literally indefinitely.

Three things the accident taught that the deliberate experiment did not:

1. **The blast radius reached a completely unrelated operation.** The Day 5 experiment was two transactions fighting over `doctors` rows. What actually got blocked five days later was a **DDL** statement — `DROP TABLE` needs `ACCESS EXCLUSIVE`, which conflicts with the row locks the abandoned transaction still holds. The victim was not another experiment; it was routine maintenance, and there was no visible connection between cause and effect.

2. **A new wait_event appeared: `Lock` / `relation`.** Day 5 only produced `Lock` / `transactionid` (waiting on another transaction's ID to finish). The `DROP` produced `Lock` / `relation` — waiting for a table-level lock. Two different lock waits with two different names, and the name tells you *what kind* of thing is being waited on. Useful diagnostic vocabulary.

3. **`idle in transaction (aborted)` is a distinct and worse state.** PID 45 was in it. That transaction had already **failed** — nothing it could still do would succeed — and Postgres was *still* holding its locks, because the transaction had not been explicitly rolled back. A transaction with zero remaining useful work was blocking real work. This state never appeared in the Day 5 experiment.

**How it was resolved:** `pg_terminate_backend` on every stale session, after which `DROP TABLE` returned immediately. Notably the fix had to come from **outside** all the participants — none of the blocked sessions could resolve it, and the culprit had no idea it was a culprit. That is the same shape as Day 2's conclusion about crashed workers: *recovery has to come from outside, because nothing inside the stuck thing can act.*

**Why it matters for Relay — this is not a tangent:**

Relay's worker will hold a transaction open around its claim. Din 3's Trap 2 is exactly this: commit the claim before executing, or the worker becomes PID 53. The Day 5 log already stated the consequence — *"a worker that crashes holding a lock on a job row prevents other workers from claiming that row, and they get no explanation why."* This incident is that sentence happening, with a five-day duration and a DDL statement as the collateral damage.

Two concrete carry-forwards:

- **`idle_in_transaction_session_timeout` should be a deliberate decision, not a default.** Postgres will not clean up after a dead or forgetful client. This belongs in `DECISIONS.md` when Relay's connection configuration is settled — probably Week 4 alongside pool sizing, since both are "unowned defaults" in the same layer.
- **Long-lived `idle in transaction` is a monitorable signal**, and the query to detect it is now known. Worth adding to whatever Week 4 observability exists, because its symptom (unrelated things hanging with no errors anywhere) is otherwise close to undiagnosable.

**Open:** the abandoned sessions survived at least one `docker compose` uptime period ("Up 2 days" while the container was created 5 days ago), which suggests the container restarted while the client sessions... could not have survived that. So the exact age of those transactions is **not established** — they may be from a later Day 5 re-run rather than the original. The states and PID roles match the Day 5 log exactly, but **"five days" is an upper bound inferred from container age, not a measured transaction age.** `xact_start` from `pg_stat_activity` would have settled it and was not captured before the sessions were terminated. Recording the uncertainty rather than the round number.
